# Portable static snapshots

Use for durable read-only evidence reports, dashboards or other structured outputs that must be regenerated from declared data. A disposable one-off visual does not require a new rendering engine. Preserve any existing versioned envelope/profile contract instead of overlaying arbitrary presentation changes on an immutable issued artifact.

## Ownership chain

The domain workflow owns facts, recommendations, uncertainty and declared assets. Visual design owns the chosen grammar and actual screenshot/readability review. The renderer owns schema validation, deterministic rendering, packaging and receipts. Delivery owns audience and attachment/publication rules. None of those roles silently authorizes the others' effects.

From an explicitly selected target root, optionally read `.agents/skill-adapters/portable-snapshots.md` for the existing engine locator, accepted schema/profile versions, build/verification commands and storage provider. Do not resolve it from this installed source root. If the required engine/schema provider is missing, report that blocked reproducibility requirement; do not silently create a second engine or label a hand-authored file deterministic.

## Build from a declared record

1. Validate source scope and the real envelope schema/version. Keep stable IDs, source revisions and local asset hashes. Unknown values and freshness limits remain explicit.
2. Select the smallest supported package: single HTML, an explicitly requested bundle, or a manifest-only reference. Do not add a source ZIP unless requested.
3. Use only the accepted typed blocks and safe asset/link fields. Do not inject arbitrary HTML, CSS, event handlers, runtime fetches or remote essential resources through data fields.
4. Build in the approved output location using the declared engine. Keep source data authoritative and generated output a dated projection, not an editable database.
5. Verify exact artifact, source and asset hashes and deterministic repeat behavior required by the contract. Read the receipt instead of equating process exit with valid output.

## Acceptance

Inspect the expected typed content, profile and asset parity. Check desktop and narrow mobile layout for overflow and actual images. If static/offline portability is promised, verify that essential content and relationships remain usable with scripts disabled and no runtime network dependence. Inspect print/PDF only when it is part of the requested product.

Run the selected domain's invariants as well as engine checks. For a comparison, displayed facts, images and outbound destinations must derive from the same record; a generic source link is not an exact purchase/action link. Do not claim freshness or access you did not verify.

Follow the target's existing writer/retention policy for canonical storage and receipts. Do not impose CAS, a queue or a second persistent payload on every user. Queued storage is not committed storage; a local attachment is not publication. Keep sensitive data in its authorized audience even when the format is portable.

Deliver the artifact and concise provenance/receipt evidence, relevant render/domain tests, remaining limits and actual publication status. Preserve unrelated repository or owner changes.
