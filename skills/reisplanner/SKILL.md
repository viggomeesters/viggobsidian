# Travel specialist router

This is an independently authored routing procedure, not a reproduction of a proprietary travel-planning implementation.

Resolve the requested result: a travel answer/comparison, a new itinerary or a bounded update to an existing itinerary. Reuse supplied dates, destination, travelers, budget, transport and constraints. Ask only for information that changes the next useful decision. Read an existing selected itinerary before an update and preserve its independent human edits.

For an explicitly selected target, inspect `.agents/skill-adapters/reisplanner.md` when present. It identifies the authorized travel specialist and any separate preservation or publication provider. Never derive a data root from this skill's installation directory. Read the actual specialist's instructions before using its capabilities; an engine URL or old checkout is not an installed runtime. If the required specialist is unavailable, state that dependent limitation and provide ordinary source-backed travel research through [research](../research/PROCEDURE.md) where useful. Do not imitate an unavailable proprietary workflow.

Travel recommendations should distinguish verified current information from assumptions, estimates and gaps. Dates and party requirements must match the actual availability/price being described. An itinerary file, booking, payment, publication and message are different effects; carry out only those actually authorized and supported. A past public URL does not authorize an update publication.

When a durable artifact is requested, let the selected output maker and travel specialist own its format and rendering. Keep audience/privacy requirements and exact local writer authority with their selected adapters. Report actual artifacts, checked source dates and remaining decisions; never label a booking or publication completed from a local preview.
