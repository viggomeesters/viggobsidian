# Clarify a decision

Start from the actual idea, desired outcome and constraints. Help with the information already available. Ask one discriminating question at a time when the user requests an interview; an ordinary design question can receive a concrete proposal directly. Do not turn a technical interview or plan into execution.

Identify the decision that changes the next step, the assumptions behind it and the evidence that would change the recommendation. Distinguish facts, interpretations, options and decisions. Compare credible alternatives on criteria derived from the user goal, including doing less where relevant. Explain the recommended direction and its practical tradeoffs. Challenge unsupported assumptions with concrete counterexamples, without manufacturing disagreement.

For a decision map, show branches, dependencies and stopping conditions at the useful level. For domain modeling, establish terms, identities, boundaries, state and ownership from actual examples before choosing implementation patterns. An architecture decision records the actual context, decision and consequences; it does not authorize repository writes by itself.

When asked for an improvement or next step, select the most valuable bounded opportunity and explain why. Advice does not start that work. For a deep quality pass, use explicit comparison criteria and a source-grounded scorecard; prioritise weaknesses that affect the goal instead of accumulating cosmetic requirements.

Teaching can use a small example or optional practice suited to the learning goal. No compulsory quiz or intake is needed. Preserve the user voice and degree of detail. Save a decision only through the proven owner and supported writer when storage is requested or established; no automatic HTML artifact.
