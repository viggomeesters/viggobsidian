# Impeccable — managed design review and refinement

This is our maintained adapter, not a byte-for-byte vendor install. Local procedure and upstream skill versions are separate identities. Public audit/output routes retain invocation; do not recreate retired standalone skills. See [upstream refresh](references/upstream-refresh.md) for provenance and selection.

## Intent and context

Read [the frontend router](../frontend/PROCEDURE.md), the actual brief and artifact/repo. Use its configured available licensed specialist for platform-specific execution and verification. Pin exact file/hash or route/state. Name the surface Read, Operate, Persuade or Experience, and whether the request evaluates, refines or redesigns. Existing product/design files, working UI and approved references provide authority. Missing PRODUCT.md or DESIGN.md is not automatically a blocker or a write request. Read `.agents/skill-adapters/impeccable.md` from the explicitly selected target root when present; a required missing specialist/provider blocks its dependent pass, not unrelated read-only analysis. Do not infer target policy from this source root.

Keep the brief, factual copy, approved identity and local boundaries leading. Vault artifacts retain their owner, writer and immutable HTML-round route; repository work retains its own execution contract.

## Smallest relevant pass

| Request | Effect |
| --- | --- |
| General review / wat zegt Impeccable? | Design critique plus relevant technical audit; findings first, artifact unchanged. |
| Critique | Judge task clarity, hierarchy, copy, relationships, visual coherence and the real reading/action path. |
| Audit | Check accessibility, focus, contrast, performance, responsive/touch/reflow and implementation integrity. |
| Typeset / layout | Inspect rendered text roles, measure, grouping and rhythm; repair only when requested. |
| Polish / harden / explicit fix | Use frontend execution, preserve the established world and fix verified in-scope defects. |
| Shape / redesign / new visual world | Use frontend's design read and plan-before-build; resolve material product choices before replacing identity. |

With no target or intent, ask for it; do not start a surprise audit. Clear intent needs no command-selection interview. Do not run every pass by default.

## Two assessments over the same target

1. **Design first:** inspect rendered representative views and states. Evaluate priority, reading order, grouping, type, density, state clarity and factual fidelity against this audience/job. Include desktop and mobile, keeping the approved style as reference.
2. **Technical evidence:** apply the configured specialist's actual platform-verification contract, run the detector when supported, and verify important findings in the browser. Exercise touch as touch where relevant and distinguish emulation from hardware. Native work uses the existing platform route.

Keep visual judgment and mechanical results separately identifiable before synthesis. The root can run sequential passes; optional delegation follows the task workflow. Numeric scores are optional and cannot imply untested coverage. Avoid invented findings and a long tail of taste preferences.

## Detector contract

An explicit Impeccable-check request runs the official detector when the environment supports it. Verify npm repository/version before a new version and pin the observed version. Record local adapter version, upstream skill commit/version, npm version and engine version when available separately. GitHub can be ahead of npm.

Follow the available specialist's verification procedure and current official detector documentation. No automatic install/update, hooks, doctor repair, provider/config mutation, or target dependency. The detector is read-only for the artifact.

Exit 0 means completed without primary findings; 2 means findings; 1 means scan failure or partial scan. Preserve stdout/stderr and effective target/config. Source-file scanning is not a full rendered-browser audit. Compare important alerts to actual computed values and interaction behavior; explain false positives or approved choices rather than adding broad ignores.

## Report and repair

Report consequential findings first: location, observed impact, evidence and bounded fix. Group alerts by cause; distinguish confirmed defects, contextual choices, false positives and unverified boundaries. Include strengths and checks actually performed. A detector count is not a usability verdict.

When repairs are authorized, prioritize blocked tasks, misleading state and inaccessible paths before cosmetics. Keep a coherent system, verify repaired behavior and inspect final screenshots. Preserve commit/publication boundaries. Store durable results at the existing owner; no second critique database or automatic HTML report is required.
