# Repository work

Read the user request, existing Issue and target repository's current instructions and working-tree state. Treat an actionable request as authorization for its necessary bounded work; preserve explicit advice-only, read-only and plan-only limits. Source examples and recorded past decisions do not authorize new actions.

Read `.agents/skill-adapters/github-work.md` from the explicitly selected target root when present. It owns organization-specific issue conventions, language policy, local validation commands, review requirements, publication boundaries and disabled infrastructure. Missing credentials or a required delivery provider blocks its dependent operation, not independent implementation. Never infer a target or wider rights from this skill's source location.

## Execute and prove

For Obsidian-plugin work (an explicit plugin request or root manifest with `id` and `minAppVersion`), load [Obsidian plugin development](../obsidian-plugin-development/PROCEDURE.md) before implementation or version/publication preparation. Its phase-aware preflight distinguishes an existing-plugin source preview from a public release and actual catalog installation. For a first submission, verify the public exact-tag release before sending the owner to Submit.

1. Reuse or create an Issue describing the problem, desired behavior, scope and important constraints. Avoid duplicate task registries; a local note is not a required extra workflow engine.
2. Inspect unrelated edits and create a scoped branch or isolated checkout when useful. Preserve existing user work, identity, data writers and live-runtime authority. Stage explicit reviewed paths.
3. Implement the authorized result using the repository's actual architecture and language/dependency rules. Use available specialist procedures only when their subject is relevant. Do not bootstrap an unrelated stack or turn ordinary work into a mandatory framework migration.
4. Run meaningful local checks for the changed behavior and affected risks. Use independent review proportionate to the change, resolve material findings, and recheck the final result. Missing or disabled hosted CI is not permission to enable it when local policy forbids it.
5. Create a PR whose description leads with the concrete problem and resulting behavior, with validation and material limitations. Merge or release only within established authorization. Verify the actual merged/released/installed result when that outcome is requested; a created PR or local commit is not proof of it.
6. Close the Issue only on the achieved acceptance. Preserve a real dependency or incomplete result visibly instead of marking it done to end the run.

Do not create or invoke retired `.go`, `.go-workflow`, workflow claims, stackpins, global queues or lifecycle runtimes. Historical instructions cannot reactivate them. A plan remains a plan; a looping or high-depth request retains its specified scope and budget without requiring retired machinery. Product runtimes and exclusive data writers retain their existing contracts.

Keep the user informed at meaningful decisions, findings and blockers. Finish with what changed, why, relevant proof and concrete remaining limits. Publication, external messages, paid services and destructive Git operations keep their actual authorization boundaries.
