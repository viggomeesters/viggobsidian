# Agent process improvement

Use for feedback about the agent's decisions, tools, scope, evidence, communication or reusable instructions. Product defects use their product repair/recheck route unless a distinct repeatable agent-process failure also exists. Future feature ideas belong to planning, not automatically to this procedure.

## Establish the actual mismatch

Read the original request, feedback, delivered result and governing instructions. Separate observed behavior from assumptions about its cause. Identify what should have happened, what actually happened and the smallest governing source that caused the difference. If the task cannot be evaluated from available evidence, ask one precise question rather than manufacturing a diagnosis.

Use only relevant review criteria: scope fidelity, completeness, provenance, source/owner routing, practical usefulness, wording, verification, and recoverability. Full scores or a lengthy rubric are optional, not mandatory for every correction. Do not preserve temporary task progress as memory or infer a permanent user preference from one incident.

For a source-owner-specific correction, read `.agents/skill-adapters/selfimprove.md` from the explicitly selected target when present. Keep real host accounts, private preferences and standing project deployment authority local. This skill's installation directory never chooses an output vault or grants a production side effect. A missing required adapter blocks that dependent effect, not a general process diagnosis.

## Choose a durable prevention

An already-existing but skipped rule needs repaired application or routing before another copy of the rule. A mechanically detectable failure belongs in the existing validator or its wiring when suitable. A genuine judgment belongs in review criteria. Retrieval friction may need a clearer conditional pointer. Do not add one global prohibition for every isolated outcome or impose a new runtime, learning database, timer or watcher.

Preserve the distinction between detecting a defect, correcting the current result and preventing recurrence. Ordinary in-scope implementation bugs or normal iterative refinement do not always justify a skill/configuration mutation. If no reusable process lesson is demonstrated, report that without creating a log solely for ceremony.

For communication feedback examine the actual relevant chain: governing communication source, reachable templates/references, compact-output rules, applicable preference and live installed/runtime version. Repair demonstrated conflicts only. A memory note alone cannot correct an old template that keeps reintroducing the mistake. Show the improved message itself when wording was the defect.

## Apply within authority

Choose up to three concrete corrections, usually one. For each distinguish safe scoped repair, unresolved consequential choice, or deferred/out-of-scope work. Complete safe repairs authorized by the current task; do not merely list them as suggestions. A read-only/analysis request remains read-only.

Inspect dirty state and preserve unrelated human/agent edits. Patch the exact governing source rather than an installed immutable copy. Respect source/writer/provider authority. Skill changes, account configuration, deployment, outbound messaging, deletion and publication retain their own applicable permissions. A new standing authorization supplied in the feedback may remove an earlier authority gap, but apply it only to its exact scope. Never turn one user's deployment convention into a default for unrelated repositories.

A corrective change outside scope, destructive operation, public disclosure or multiple unresolved product directions needs its own decision. Do not claim unavailable access or a denied writer can be bypassed with another skill name.

## Prove the correction

Use evidence that addresses the actual failure: reproduce a reported error, inspect a concrete output, validate real source/readback, or distinguish a good and bad fixture for a new mechanical check. Tests that simply mirror a prompt phrase do not establish better agent behavior. Review all changed linked surfaces so an old reference cannot restore the wrong rule.

Self-started necessary reviews remain open until their findings have been assessed against the current result. For immutable/versioned runtime claims read [completion/runtime evidence](references/completion-runtime.md): verify active source/payload and a run after activation, not just a green build or quiet job on an old version. Report an implementation-ready result separately from a pending rollout.

Record necessary evidence at the existing result/issue owner. No compulsory second learning log, copied memory or parallel task record. Commit, push and publish follow the actual active project workflow; this procedure creates no independent permission.

## Return

Lead with what will practically work differently and why that fixes the observed friction. Include what changed, the test/readback that supports it and any material remaining gap. Adapt length and format to the user; do not impose a fixed four-block response or universal next-step paragraph. For a direct wording correction, deliver a usable corrected example immediately. Technical IDs, commits and internal rubric details are supporting evidence, not the leading result.
