# Choose the next improvement

Read the original request, current result, actual findings and feedback. Use the smallest relevant source/diff/test context; do not rediscover the entire project or reopen another owner's ongoing work without new evidence.

First distinguish incomplete acceptance from a new opportunity. A missing requirement in the current task still belongs to that task and its execution/recheck route. An independent investigation belongs to audit; a direction decision before building belongs to brainstorm. Do not create a new backlog to make a recommendation look substantial.

Usually recommend one next step. Offer at most a few alternatives only when they present a genuine choice. State the trigger, expected value, bounded scope and observable acceptance. Compare effort, risk and dependencies. Stop or gather practice evidence when that is more valuable than more change; do not invent an improvement.

A question such as “what next?” requests advice. It does not authorize filewrites, task creation or easy fixes. “Do it” can approve an already concrete bounded proposal; use that context and do not ask again when its outcome and limits are clear. Where several incompatible actions remain possible, ask only the missing choice.

For authorized persistence or execution, use the actual owner and its supported writer/repository workflow. Do not create a global queue or use retired workflow machinery. External effects, deployment, publication and messages retain their own authority. A saved proposal is not an executed proposal.

Return the recommended action and why it matters now, then enough scope and acceptance to make it actionable. Add only a real dependency or useful alternative, not a fixed report template.
